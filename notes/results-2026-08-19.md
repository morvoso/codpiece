Prod's deployed config reaches ~50 tok/s using tensor split + MTP
speculative decoding, neither of which tandem has yet — that is M3e and M4,
not a like-for-like comparison with the number above.

Layer split is the *correctness* path, not the fast one: the scheduler
re-plans every step, the cached decode graph is disabled, and all session
KV/state sits on device 0. Tensor parallel (M3e) is what prod's `-sm tensor`
uses and what closes this gap.

## Speculative decoding (MTP), Qwen3.8-27B, tensor parallel

Lossless by construction — a draft is kept only when it equals what the
trunk would have produced — and verified as such: `spec` output is identical
to plain greedy at every depth tested.

| mode | decode tok/s | acceptance | tokens/round |
|---|---|---|---|
| plain greedy | 40.1 | — | 1.00 |
| MTP depth 1 | 47.9 | 0.900 | 1.92 |
| MTP depth 2 | 52.9 | 0.713 | 2.40 |
| MTP depth 3 | 59.2 | 0.667 | 3.00 |

### Head to head with llama.cpp's own server (3 reps each, one window)

This is the honest comparison, and tandem does **not** win it yet:

| engine | decode tok/s |
|---|---|
| llama.cpp b10423 server, prod MTP config (`draft-mtp`, n-max 3, p-min 0.75) | **65.0** |
| tandem, MTP depth 3 | 59.2 (**91 %**) |

**Correction to an earlier claim in this file:** tandem's 59.2 was briefly
described as beating production's "~50 tok/s". That was wrong — the ~50 in
ENGINE.md was measured under a heavier configuration (196K context
allocation, `-np 2`). Measured side by side at matched settings, llama.cpp
does 65.0 and is still ahead.

### Where the speculative gap actually is (measured, not guessed)

Confidence gating (`--p-min`, llama.cpp's `--spec-draft-p-min`) was the
obvious suspect. It was implemented and swept on the 27B — and it is **not**
the answer:

| draft depth | p-min 0.0 | 0.4 | 0.6 | 0.75 |
|---|---|---|---|---|
| 3 | 57.8 | **58.3** | 56.3 | 54.2 |
| 4 | 55.4 | 57.4 | 58.0 | 54.7 |
| 5 | 51.8 | 53.6 | 56.1 | 53.3 |

Acceptance moves a lot (0.67 → 0.86) while throughput sits at 54–58
regardless. The arithmetic locates the real cost: a round yielding 3 tokens
takes 52 ms, about 2.1 plain decode steps, so each draft from a **one-layer**
head costs ~8 ms — while its LM projection is only ~1.4 ms of bandwidth. The
rest is graph construction and allocation per draft.

Caching the draft graph (the same trick that gave the trunk's decode step its
CUDA-graph win) is implemented and lossless on CPU, but the tensor-parallel
meta backend rejects the cached graph, so the 27B still pays the rebuild.
That is the next concrete piece of work, and it is worth roughly the whole
remaining gap to llama.cpp.

The 48 recurrent layers are what makes this hard on a hybrid model: they
cannot be run backwards, so rejected drafts are undone from K state
snapshots (the fused GDN op emits them; conv state gets K trailing windows).

## Ideas specific to this machine (2026-08-20)

Two changes that a general-purpose engine would not make, both following from
the same observation: on 2×3090 with no NVLink, **VRAM and CPU are abundant
while PCIe and GPU-time are scarce**, and decode is bandwidth-bound so a
verify pass costs one weight-read no matter how many tokens ride along.

**1. Replicate the LM head instead of splitting it.** Splitting
`output.weight` saves ~0.7 GiB per card but forces 3.9 MB of logits across
PCIe for every scored position, because a column-split vocabulary cannot be
argmaxed inside the graph. Replicating it costs VRAM this box has spare and
ships 4 bytes per position instead. (`TANDEM_SPLIT_OUTPUT=1` restores the
memory-optimal split.)

**2. Draft on the CPU, for free.** The MTP head is a real transformer block
(~8 ms per draft on the 27B), so its deeper drafts are a bad trade at 0.67
acceptance. The 24-thread CPU and 62 GiB of RAM are idle during every decode
step, so `oracle.rs` predicts continuations from the live token stream there —
in microseconds, off the GPU entirely. It is strong exactly where
transformers spend tokens (quotation, repeated identifiers, list and bracket
scaffolding) and declines otherwise, which is right: an empty draft slot is
free, a wrong one costs a rollback.

Measured (0.8B, raw continuation of natural text): **0.750–0.800 acceptance
on oracle drafts, at zero GPU cost.**

### …and the honest outcome on the 27B: it does not pay

The hypothesis was that free CPU drafts would widen each speculative round at
no cost. On the real model they cost more than they return, on both workloads
tried (same window, same prompt, lossless throughout):

| workload | MTP depth 3 alone | + oracle | oracle acceptance |
|---|---|---|---|
| revise/reproduce given text | **48.1 tok/s** | 44.6 | 0.233 |
| write new code | **54.0 tok/s** | 51.3 | 0.056 |

Two reasons, both measurable:

1. **Acceptance collapses on the larger model.** The 0.8B was continuing raw
   wikitext, where token-level n-grams repeat heavily. The 27B answers in
   chat: it paraphrases rather than quoting, and reasons before it writes. The
   redundancy the predictor feeds on largely is not there.
2. **A draft slot is not actually free on a hybrid model.** Each extra slot
   widens the verify batch *and* adds one recurrent-state snapshot write per
   GDN layer — about 300 MB of device copies per round for two extra slots
   across 48 layers. The "extra tokens ride along for free" intuition holds
   for attention-only models; the recurrent half of this one charges for them.

The oracle is kept (defaults **off**, `--oracle N` to enable) because it is
lossless, self-limiting, and clearly right on quotation-heavy raw
continuation — but it is not on by default, and the claim that it helps the
27B is **withdrawn**.

The measurement also refutes the other hypothesis of the session: replicating
the LM head removed ~15 MB of per-round PCIe traffic and moved throughput by
less than run-to-run noise. The readback was not the bottleneck either.

## Bugs found, and what found them

| bug | found by | why it was invisible before |
|---|---|---|
| all-f32 KV caches corrupt on CUDA | GPU self-test | CPU kernels are fine; only CUDA's V transposed-write/padded-read path breaks |
| device-side mask never initialized | GPU self-test | CPU's synchronous fallback masked it |
| graph inputs treated as persistent across computes | 2,334-token parity run | allocator only overlapped the input at large n_kv |
| `GGML_CUDA_GRAPHS` off by default in standalone ggml | A/B with `GGML_CUDA_DISABLE_GRAPHS` | debug logs are compiled out; the logits copy hid the effect |
| scheduler needs a CPU backend last | 2-GPU run | documented only as an assert |
