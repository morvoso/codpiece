### Where the speculative gap actually is (measured, not guessed)

Confidence gating (`--p-min`, llama.cpp's `--spec-draft-p-min`) was the
obvious suspect. It was implemented and swept on the 27B — and it is **not**
the answer:

| draft depth | p-min 0.0 | 0.4 | 0.6 | 0.75 |
|---|---|---|---|---|
| 3 | 57.8 | **58.3** | 56.3 | 54.2 |
| 4 | 55.4 | 57.4 | 58.0 | 54.7 |
| 5 | 51.8 | 53.6 | 56.1 | 53.3 |

Acceptance moves a lot (0.67 → 0.86) while throughput sits at 54–58
regardless. The arithmetic locates the real cost: a round yielding 3 tokens
takes 52 ms, about 2.1 plain decode steps, so each draft from a **one-layer**
head costs ~8 ms — while its LM projection is only ~1.4 ms of bandwidth. The
rest is graph construction and allocation per draft.

Caching the draft graph (the same trick that gave the trunk's decode step its
CUDA-graph win) is implemented and lossless on CPU, but the tensor-parallel
meta backend rejects the cached graph, so the 27B still pays the rebuild.
That is the next concrete piece of work, and it is worth roughly the whole
remaining gap to llama.cpp.

The 48 recurrent layers are what makes this hard on a hybrid model: they
cannot be run backwards, so rejected drafts are undone from K state
snapshots (the fused GDN op emits them; conv state gets K trailing windows).

## Ideas specific to this machine (2026-08-20)

Two changes that a general-purpose engine would not make, both following from
the same observation: on 2×3090 with no NVLink, **VRAM and CPU are abundant
while PCIe and GPU-time are scarce**, and decode is bandwidth-bound so a
verify pass costs one weight-read no matter how many tokens ride along.

**1. Replicate the LM head instead of splitting it.** Splitting
`output.weight` saves ~0.7 GiB per card but forces 3.9 MB of logits across
PCIe for every scored position, because a column-split vocabulary cannot be
argmaxed inside the graph. Replicating it costs VRAM this box has spare and
ships 4 bytes per position instead. (`TANDEM_SPLIT_OUTPUT=1` restores the
memory-optimal split.)

**2. Draft on the CPU, for free.** The MTP head is a real transformer block
(~8 ms per draft on the 27B), so its deeper drafts are a bad trade at 0.67
acceptance. The 24-thread CPU and 62 GiB of RAM are idle during every decode
step, so `oracle.rs` predicts continuations from the live token stream there —
in microseconds, off the GPU entirely. It is strong exactly where
transformers spend tokens (quotation, repeated identifiers, list and bracket
scaffolding) and declines otherwise, which is right: an empty draft slot is
free, a wrong one costs a rollback.

Measured (0.8B, raw continuation of natural text): **0.750–0.800 acceptance
on oracle drafts, at zero GPU cost.**

### …and the honest outcome on the 27B: it does not pay

The hypothesis was that free CPU drafts would widen each speculative round at
no cost. On the real model they cost more than they return, on both workloads
tried (same window, same prompt, lossless throughout):

| workload | MTP depth 3 alone | + oracle | oracle acceptance |
|---|---|---|---|
| revise/reproduce given text | **48.1 tok/s** | 44.6 | 0.233 |
| write new code | **54.0 tok/s** | 51.3 | 0.056 |

Two reasons, both measurable:

1. **Acceptance collapses on the larger model.** The 0.8B was continuing raw
   wikitext, where token-level n-grams repeat heavily. The 27B answers in
   chat: it paraphrases rather than quoting, and reasons before it writes. The
   redundancy the predictor feeds on largely is not there.
2. **A draft slot is not actually free on a hybrid model.** Each extra slot
   widens the verify batch *and* adds one recurrent-state snapshot write per
   GDN layer — about 300 MB of device copies per round for two extra slots
   across 48 layers. The "extra tokens ride along for free" intuition holds
   for attention-only models; the recurrent half of this one charges for them.

The oracle is kept (defaults **off**, `--oracle N` to enable) because it is
lossless, self-limiting, and clearly right on quotation-heavy raw
continuation — but it is not on by default, and the claim that it helps the
27B is **withdrawn**.

The measurement also refutes the other hypothesis of the session: replicating
the LM head removed ~15 MB of per-round PCIe traffic and moved throughput by
less than run-to-run noise. The readback was not the bottleneck either.

# 2026-08-20: graph caching under tensor parallelism

The limit recorded earlier — "under tensor parallelism the meta backend
supports exactly one repeatedly-replayed graph per session" — turned out to be
a lifetime bug in `ggml-backend-meta.cpp`, not a property of the design. It is
fixed, and the first speculative configuration is now cached.

## What was actually wrong

The meta backend maps each meta tensor to one simple tensor per device in a
`std::map` **keyed by raw tensor pointer**, held in a rotating pair of
"compute" containers. Registration happened at *allocation* time, while
eviction is driven by which graph is being *computed*. Those two orders agree
only while a single graph is replayed forever. With two, a rebuild empties a
container the other graph still has live cross-references into.

Three separate defects fell out of that, each found by a different symptom:

| symptom | cause |
|---|---|
| `GGML_ASSERT(bcj.nodes[i])` at ggml-backend-meta.cpp:1838 | a replayed graph's views had been evicted by another graph's rebuild; nothing re-created them |
| flash-attention node with `K=cache_gdn_l6`, `V=cache_conv_l8` | tensors were re-created, but tensors that had *survived* still held `src` pointers into the emptied container, which now aliased whatever landed at those addresses |
| same aliasing, from tandem's side | `rollback_recurrent` built its graph in a context it freed each round, so the heap handed the same addresses to different tensors |

The fixes are correspondingly three:

- **ggml**: a rebuild now commits the container flip and re-registers the whole
  graph into the container it just emptied, so every tensor in a graph is
  created in one pass and their `src` pointers only ever refer to each other.
- **tandem**: rollback graphs are built once per rollback distance and kept for
  the life of the session (there are only `k_slots` of them).
- **tandem**: a superseded cached graph's context is retired to a graveyard
  rather than freed, so its addresses cannot be recycled underneath the map.

`build.rs` also never tracked the vendored ggml sources, so a ggml edit did not
trigger a rebuild — meaning a patched backend could silently not be in the
binary. Now fixed; worth remembering before trusting any ggml-level A/B.

## Candidate-restricted draft vocabulary — refuted, but informative

Projecting the draft head onto a shortlist instead of all 248,320 rows is
lossless by construction: verification always uses the full vocabulary, so a
shortlist miss costs that draft and nothing else. It does make rounds cheaper —
43.6 -> ~39 ms at depth 2, which pins the draft LM projection at ~2.2 ms of each
~5.4 ms chain step. But acceptance falls from 0.712 to 0.37-0.44 and throughput
with it (55.5 -> ~46).

The size sweep is the interesting part: 2048 -> 16384 candidates moved
acceptance only 0.370 -> 0.430, so the true argmax sits outside even a 16K
shortlist most of the time. Low token ids are a poor frequency proxy in this
248K multilingual vocabulary. Break-even needs acceptance >= 0.585, so the idea
is only worth revisiting with a shortlist ranked by measured token frequency.
Kept behind `--cand N`, defaults off.

## The accuracy question this raised, and its answer

The three-prompt losslessness gate caught something the single-prompt gate had
been missing: on the Python prompt, fused speculative output **differs** from
tandem's own single-token greedy decoding, at every depth.

What it is not:

- not the graph caching — the cached and rebuilt paths produce *identical*
  output to each other (same acceptance, 62/66, same round count), both
  differing from greedy;
- not nondeterminism — plain greedy is stable across reruns;
- not a drafting error — a draft is committed only when it equals the trunk's
  own argmax at that position, so no committed token is ever draft-invented.

What it is: verifying T tokens in one batch is not bit-identical to decoding
them one at a time, so a near-tied argmax can flip. **llama.cpp's own MTP
speculation diverges from its own greedy output on the same prompt at the same
token** — and both engines' non-speculative greedy outputs agree with each
other word for word. This is a property of batched speculative decoding on
this model, and tandem matches the reference implementation's behaviour.

`scripts/specparity-payload.sh` reproduces the llama.cpp half;
`scripts/final-verify.sh` is the three-prompt gate that should be run instead
of the single-prompt one from now on.

## A second meta-backend bug, found by adaptive depth

Adaptive draft depth segfaulted inside `ggml_backend_meta_graph_compute` at 160
tokens but not at 32, and `--max-depth 2` survived while 3 and 5 did not — the
clue being that max-depth 2 admits only four graph shapes.

When the meta backend grows its per-device graph pool it does:

```c
backend_ctx->max_subgraphs = std::max(backend_ctx->max_subgraphs, n_subgraphs);
...
backend_ctx->ctx.reset(ggml_init(params));      // invalidates every cgraph_main
for (j) for (i = 0; i < n_subgraphs; i++)       // ...but refills only this graph's
    bcj.cgraphs[i].cgraph_main = ggml_new_graph_custom(...);
```

The reset invalidates all `max_subgraphs` slots; the refill covers only the
current graph's `n_subgraphs`. A graph with *more* subgraphs that ran earlier
does not re-enter this branch later (its count no longer exceeds
`max_subgraphs`), so on its next replay it reads slots above `n_subgraphs` as
dangling pointers into a freed context.

It needs graphs of differing subgraph counts to be replayed in turn, which is
precisely what adaptive depth does and what llama.cpp never does — one graph
shape at a time. The fix refills all `max_subgraphs` slots, sized by
`max_nnodes`, which is what `mem_per_device_graphs_main` already budgets for.

Same family as the first bug: state sized for the maximum over all graphs, but
maintained as though only one graph existed.

## Adaptive draft depth

The three-prompt sweep is what motivated it — the best fixed depth is different
for each prompt, and no single default is right for all of them:

| prompt | d1 | d2 | d3 | d4 | d5 |
|---|---|---|---|---|---|
| why the sky is blue | 57.8 | **64.4** | 63.1 | 56.6 | 51.0 |
| merge two sorted lists (code) | 61.3 | 65.0 | **68.4** | 64.1 | 61.6 |
| first ten primes and their sum | 63.0 | 77.1 | 89.3 | **90.3** | 88.2 |

`--depth auto` picks per round by maximising `E(K)/T(K)`, where `E(K)` comes
from the per-position acceptance a round already reports and `T(K)` is a
measured round time.

### The finding that made it work: acceptance RISES along the chain

Consecutive depths give the conditional acceptance at each chain position
(`tokens/round = 1 + p1 + p1p2 + ...`). Measured on 128-token runs:

| prompt | p1 | p2 | p3 | p3/p2 |
|---|---|---|---|---|
| prose | 0.88 | 0.72 | 0.63 | 0.89 |
| code | 0.94 | 0.55 | **1.00** | **1.81** |
| arithmetic | 1.00 | 0.91 | ~1.00 | 1.17 |

On the code prompt the *third* draft is accepted every single time. This is a
survivorship effect and it is obvious in hindsight: position 3 is only ever
reached when positions 1 and 2 were accepted, and that selects for a locally
predictable stretch of text, where the next draft is likely right too.

The first version assumed the opposite — a prior that decayed along the chain —
so it mis-priced exactly the case where depth pays, and sat at depth 2 on code
while depth 3 was 5% faster. Two changes fixed it:

- the prior for an unmeasured position inherits its predecessor **flat**, not
  discounted;
- scoring uses an optimism bonus (`0.3 / sqrt(n + prior)`) so an unmeasured
  depth is worth one visit. Without it, position K+1 can never be priced at
  all, because it is only observable by going there.

Code-prompt throughput went 63.8 -> 67.8 tok/s on that change alone.

### Where it ended up

| prompt | d1 | d2 | d3 | **adaptive** |
|---|---|---|---|---|
| sky (128 tok) | 58.7 | 65.8 | 65.7 | **65.7** |
| code (128 tok) | 60.4 | 64.4 | 66.7 | **66.9** |
| primes (128 tok) | 62.5 | 76.9 | 87.5 | **87.6** |
| mixed prose+code+table (320 tok) | 58.5 | **67.6** | 65.8 | 65.9 |

Adaptive ties or beats fixed depth 3 on all four, without being told the depth.
It does not reach the per-prompt best on the mixed prompt, and the reason is
understood: that generation ends in a highly predictable markdown table, so the
decayed acceptance estimate is pulled up by the recent text (p3 reads 0.75 while
the whole-run value is 0.56) and depth 3 keeps looking right. The picker is
optimising the text it is currently in, which is the intended behaviour; the
run-average verdict just disagrees.

### Two things measured and discarded

**Faster forgetting.** A ~69-round half-life looks far too long to track a
generation moving from prose into code into a table, so 0.95 (~13 rounds) was
tried. It measured *worse* on three of four prompts: the extra responsiveness
buys estimator noise and more switching, not tracking.

**Forcing a calibration visit to the shallower depth.** The slope of `T(K)`
needs two timed depths, and the optimism bonus only ever argues for going
deeper, so a picker that settles never times its shallower neighbour. Forcing
one visit per six rounds until it has samples cost **8%** on a 46-round
generation — a shallower round also produces one fewer draft for the round
after it. Removed; depths the picker moves between on its own supply the second
timing whenever it moves at all.

### A correction

An earlier reading here claimed the per-chain-step cost rises with context
(6.05 ms at ~180 tokens, 12.7 ms at ~320) and that this inverted the depth
ranking on long generations. **That is withdrawn.** Measured directly —
ms/round at depths 1/2/3 for generations of 128, 256 and 512 tokens:

| tokens | d1 | d2 | d3 |
|---|---|---|---|
| 128 | 32.0 | 37.6 | 44.1 |
| 256 | 31.9 | 37.8 | 44.1 |
| 512 | 31.9 | 37.9 | 44.9 |

5.6-7.0 ms per step with no trend in context. The 12.7 ms figure came from
applying one run's acceptance profile to a different run's throughput, which is
not valid — acceptance depends on the batch, and the batch depends on the depth.

# 2026-08-20: long context

Everything to this point was measured at `-c 4096`, while production serves this
model at 196K and M5's gate assumes that works. Two things came out of actually
running it: a real bug in speculative decoding, and a concrete ceiling.

## Decode barely notices the context

| prompt tokens | plain prefill | plain decode | fused d3 decode |
|---|---|---|---|
| 973 | 1,348 tok/s | 39.0 | 52.7 |
| 9,230 | 1,462 | 38.3 | 40.3 |
| 26,656 | 1,376 | 37.1 | 46.6 |
| 62,021 | 1,227 | 35.4 | 49.9 |
| 94,454 | 1,077 | 32.6 | 44.1 |
| 126,917 | 960 | 31.4 | (see below) |

Decode falls only ~20% from 1K to 127K tokens of context, which is the hybrid
architecture paying off: 48 of the 64 layers are Gated DeltaNet recurrences
whose state is a fixed size no matter how long the sequence is, and only 16 are
attention. Prefill degrades more (quadratic attention over those 16 layers)
but stays around 1,000 tok/s at 127K.

**Arithmetic worth writing down, because I got it wrong once mid-session:** the
KV cache is 4 heads x 256 dims x 2 bytes x 2 (K and V) = 4 KiB per token *per
attention layer*, and there are 16 of them — **64 KiB/token**, so 196K context
is 12.9 GiB, not the 0.75 GiB a missing 16x factor suggested.

## The bug: speculation died above ~9K tokens

`fused` aborted on any prompt past about 9K tokens while plain decoding was
fine. The fused round asks the trunk for predictions at *every* position,
because that is what verification compares against — and at prefill that
materialises a logits tensor of `n_vocab x n_prompt`: 248,320 x 26,656 x 4 B =
**26 GiB**. It simply fails to allocate.

Fixed by prefilling in chunks of 256. Two details mattered:

- The draft head consumes exactly the positions the trunk emits, so asking for
  only the last position (tried first) also stops the head from seeing the
  prompt, and its KV cache is what makes early drafts good. That version was
  lossless but shifted acceptance on every prompt — down 0.98 -> 0.86 on one,
  up 0.73 -> 0.86 on another. Chunking keeps the semantics identical instead:
  acceptance figures match the pre-change values exactly.
- Only the final chunk's drafts are ever read, so earlier chunks run at depth 1.
  That cut the prefill cost of speculation from +41% over plain to +25%.

## The ceiling, and what sets it

| context | plain | fused (speculative) |
|---|---|---|
| allocation only, short prompt | works to 200,704 | — |
| 62K tokens | works | works |
| 94K tokens | works | works |
| 127K tokens | works | works **only with a smaller prefill chunk** |
| 194K tokens | out of memory | out of memory |

At 127K a 256-token prefill chunk cannot allocate its graph at all, while a
64-token chunk runs and decodes at **52.3 tok/s against plain's 32.1** — a 1.63x
speculative speedup at 130K of context. Prefill pays for it: 643 tok/s versus
976 plain. Going further down to 16 helps nothing and costs a lot (285 tok/s).

The chunk size therefore scales with context — `2^23 / n_ctx`, clamped to
[64, 256], so 256 up to ~32K and 64 by 130K — with `TANDEM_PREFILL_CHUNK` to
override. Short-context behaviour is unchanged: acceptance figures at 4K match
the pre-change values exactly.

Per card: 14.65 GiB of weights, plus half the KV cache, plus compute buffers.
At 194K that is 14.65 + 6.6 = 21.3 GiB of a 24 GiB card before a single graph
is built, and the cards were observed completely full (24,118 MiB). Production
fits 196K because llama.cpp keeps one graph shape; tandem caches several, each
owning a compute buffer holding a mask of `n_kv x chunk` and logits of
`n_vocab x chunk`.

The speculative path fails a step earlier than plain because it also holds an
MTP KV cache over the whole context, `k_slots` recurrent snapshots, and more
cached graph shapes. `Session::clear_fused_cache()` drops the prefill shapes
once prefill is done — they are never used again — but that alone did not move
the ceiling, because the allocation that fails happens *during* prefill, not
after it. What moved it was the chunk size.

## Production context reached (plain), and exactly why speculation cannot follow

Scaling the prefill chunk turned out to be the whole story for plain decoding:
**a 186,162-token prompt now runs at -c 200704, decoding at 28.1 tok/s** with
prefill at 813 tok/s. Production's context, on tandem, with no flags.

Speculation still does not fit there, and the reason is specific rather than
general. Compute buffers are not the problem — traced with `TANDEM_TRACE_MEM=1`
they are 3.1 MiB for a decode graph and 12.6 MiB for a fused one, flat in
context. The problem is that two tensors are **replicated on both cards instead
of split**:

| tensor | stored as | size |
|---|---|---|
| `output.weight` | BF16 | 2.368 GiB |
| `token_embd.weight` | Q8_0 | 1.258 GiB |

Mirroring costs **1.81 GiB per card** (16.46 GiB rather than the 14.64 a naive
half-of-total suggests), and it is deliberate: the fused speculative round does
`argmax` and the embedding gather *inside* the graph, and neither is expressible
on an axis-0-split tensor under this backend. The draft head has no embedding or
head of its own — `blk.64` is just `nextn.eh_proj/enorm/hnorm/shared_head_norm`
— so it shares both.

So at 196K it is speculation or production context, not both:

| | per card |
|---|---|
| weights, mirrored (speculation possible) | 16.46 GiB |
| weights, `TANDEM_SPLIT_OUTPUT=1` (plain only) | 15.28 GiB |
| KV at 196K | 6.12 GiB |
| draft head's own KV, uncapped | 0.38 GiB |

Splitting the LM head costs nothing measurable in speed — 29.2 vs 28.1 tok/s at
186K, 39.3 vs 39.0 at 4K, the host-side argmax being ~1 MB per token — but it
disables the fused round outright.

**Bounding the draft head's window** (`TANDEM_MTP_CTX`, default 16384) recovers
0.35 GiB per card. It is lossless by construction — every draft is verified
against the full model, so a shorter window can only cost acceptance — and at 4K
it changes nothing measurable (acceptance 0.629 at depth 3, identical to before).
It moved the speculative ceiling from ~127K to **145K tokens**.

# 2026-08-20: M5a — samplers

Everything before this decoded greedily, because the accuracy gate is temp-0
parity. `tandem-sample` adds temperature, top-k, top-p, min-p and
repeat/frequency/presence penalties, with a seeded xoshiro256++ draw.

Filter semantics are ported from llama.cpp's `llama-sampler.cpp` at the pinned
build rather than reinvented, so a request means the same thing to both engines.
The details that are easy to get wrong and are matched deliberately:

- **top-p includes the crossing token** — the running sum is checked *after*
  adding each probability, and the index kept is `i + 1`.
- **min-p is a threshold on the logit**, not a probability scan:
  `p_i >= min_p * p_max` is exactly `logit_i >= max_logit + ln(min_p)`, which is
  why it can filter a 248K vocabulary without sorting it.
- **the repeat penalty checks the sign**: dividing a negative logit by the
  penalty would make a discouraged token *more* likely, so a non-positive logit
  is multiplied instead.
- **temperature comes last**, after the filters, so they see untempered
  probabilities.

Performance matters here in a way it does not for a 32K vocabulary: a full sort
of 248,320 candidates per token would cost more than the forward pass. Every
path narrows first — `select_nth_unstable` for top-k, the logit threshold for
min-p — and sorts only the survivors.

**Verified on the 27B**: `--top-k 1 --temp 1` reproduces greedy decoding token
for token while going through the host sampling path, which exercises the
readback, the candidate set and the draw at once. Greedy 39.02 tok/s, top-k-1
38.46 — so a vocabulary of logits per step costs ~1.5%, and `is_greedy()` keeps
the in-graph argmax whenever the parameters allow it. Seeded runs reproduce;
different seeds differ; sampled text is coherent.

**What sampling parity does not mean:** llama.cpp draws with `std::mt19937`
through `std::discrete_distribution`, whose stream is implementation-defined.
A seeded tandem run matches itself, never llama.cpp token for token. Token-exact
parity remains a temperature-0 claim — which is what every existing gate checks.

# 2026-08-20: M5b + M5c — the server, and speculation at temperature

## M5b: `tandem serve`

OpenAI-compatible: `/v1/chat/completions`, `/v1/completions`, `/health`,
`/v1/models`, `/slots`, SSE streaming, CORS. HTTP/1.1 written against

The chat template was the only real risk. It ships inside the GGUF, it is
authoritative, and Qwen3.5's is ~10 KB of Jinja using macros, `namespace()`
counters, `is iterable` / `is mapping` tests and whitespace control. Guessing at

and call Python string methods (`startswith`, `split`), which are not Jinja and
which minijinja does not implement; `minijinja_contrib::pycompat` is the shim for

**Gate: a greedy request over HTTP is byte-identical to `tandem gen`.** That one
check exercises the socket, the JSON, the template, the tokeniser and the
sampler at once.

## M5c: speculation above temperature 0

This was flagged as the item that might force a redesign of the fused graph. It
did not, and the reason is worth writing down.

The concern was that keeping a draft because it equals the trunk's argmax is
exact only at temperature 0, and that the general rule — accept with
`min(1, p_target(x)/p_draft(x))`, else draw from the normalised residual —
needs *draft* probabilities, which the fused graph does not emit.

But the draft head proposes its **argmax**, so the draft distribution is a point
mass: `q = delta_x0`, `q(x0) = 1`. The rule collapses to

- accept `x0` with probability `p(x0)`;
- otherwise draw from `p` with `x0` removed and renormalised.

which emits exactly `p`:
`P(x0) = p(x0)`, and `P(y) = (1 - p(x0)) * p(y)/(1 - p(x0)) = p(y)`.

Only the *target* distribution is needed — the one the sampler already builds.
And at temperature 0 the target is itself a point mass on the argmax, so
`p(draft)` is 1 exactly when the draft equals it: the same rule, one code path.

What it cost: the trunk's logits have to come back to the host for sampled
requests (`n_vocab x n_out`, ~4 MB at four positions). Greedy keeps the in-graph
argmax and reads nothing.

| through the server | before | after |
|---|---|---|
| greedy | 39.6 tok/s | **73.5** |
| temp 0.7, top_p 0.9 | 35.1 | **62.5** |

A property test draws 200,000 times through the acceptance rule and asserts the
emitted frequencies match the target distribution to within 0.005.

### A sampler bug this surfaced

The first sampled measurement was 35.1 tok/s — *slower* than not speculating.
With `top_p` set and `top_k` unset, the candidate builder was sorting all
248,320 entries, per position, per round. Now it normalises in O(n), takes a
probe of the largest 1,024 and widens only if those do not already cover `top_p`.
Same fix for the penalty lookup, which was a linear scan over the window for
every token in the vocabulary — 16M comparisons per sampled token at a 64-token
window. Both are the kind of thing a 32K-vocabulary engine never notices.

# 2026-08-20: the box's own benchmark, against both engines

`~/llm/bench/db2.py` is what M5's gate names, so the first job was to make it run
**unmodified**. Reading it turned up exactly what was missing, and running it

Missing and now added: `POST /tokenize` (and `/detokenize`), the `timings`

## The bug it found: a session per request

The first run aborted at the second depth with *"slot 0 busy — another client is
on the server"*. It was not a false alarm and not a race worth papering over:
the engine was building a `Session` per request and dropping it afterwards, and
at `-c 131072` that is 4+ GiB of KV cache. `cudaFree` synchronises, so the
teardown outlived the response — the client had its answer while the slot still
read busy. The same code on CPU with `-c 2048` looked perfect, which is why a
small-model smoke test had missed it.

Fixed by building one session for the life of the process and resetting it
between requests, which is the right shape anyway: no request should be paying
multi-gigabyte allocation and a device synchronise.

## The prefill gap was mine

The benchmark said tandem prefilled at 820 tok/s against prod's 1353. That is not
an engine gap:

| -c 131072, 33.5K prompt | tok/s |
|---|---|
| trunk only, chunk 64 | 848.6 |
| trunk only, chunk 512 | **1330.5** (prod: 1353.2) |
| speculative, chunk 64 | 818.1 |
| speculative, chunk 128 | 983.8 |
| speculative, chunk 256 | **out of memory** |

Prefill is compute-bound, so a small chunk starves the GPU. The speculative round
cannot use a big one — its logits tensor is `n_vocab x chunk` — and when I shrank
the chunk to fit 196K context I scaled it off `n_ctx` and applied it to *every*
prefill. That one choice was the whole difference.

Fixed by splitting prefill: the bulk of the prompt goes through the trunk at a
large chunk, and only the last 64 tokens through the speculative round, which is
all that is needed to leave the draft head's cache warm and produce the first
drafts. **1337.4 tok/s** on the benchmark now, against prod's 1353.2.

Choosing the chunk taught something too. The obvious rule — scale it up as
context shrinks — is wrong at the top end, because what binds is the memory left
after the weights and the KV cache, not the context itself:

| -c | KV/card | free | best chunk measured |
|---|---|---|---|
| 131,072 | 4.00 GiB | ~3.0 GiB | 512 (1331 vs 849 at 64) |
| 200,704 | 6.12 GiB | ~0.9 GiB | 64 (815 vs 685 at 334) |

At 196K the *larger* chunk is slower — there is no room for the mask. The rule
now follows the headroom, and it is a two-point fit, which the code says out loud.

## Serving fixes that came out of running the real benchmark

- **The slot was reported busy after the answer was sent.** First cause was a
  `Session` built per request (4+ GiB of KV at a long context; `cudaFree`
  synchronises). Fixed by keeping one session and resetting it. The report came
  back anyway, because `assert_idle` is the *first* line of the benchmark's next
  call — the window is microseconds, not milliseconds. The counter now drops
  *before* the terminal event is sent: a request is finished when the client can
  see it is, not when the worker gets round to bookkeeping.
- **The server hard-required an MTP head.** Routing prefill's tail through the
  fused round broke every model without a draft head. `has_mtp()` now selects a
  plain path; verified on the 0.8B, greedy and sampled.
- **Adaptive depth in the server: measured worse, reverted to fixed 3.**
  44.2 tok/s against 46.5 at 32K depth. That is the third independent time
  adaptive has come out neutral-or-worse; it stays available behind `--depth 0`.
- `--draft-gate P` is implemented — decline to draft deep when the target
  distribution at this position is flat, the same idea as production's
  `--spec-draft-p-min 0.75` measured off a signal tandem already has. **Not yet
  measured**; it defaults off.

## The draft gate: measured, does not help

Production runs `--spec-draft-p-min 0.75` and reports 0.78 acceptance at

|---|---|---|

with `p-min` filtering the denominator. The two numbers are not measuring the
same thing, and tandem's is close to the ceiling for ungated drafting.

## Two more serving bugs, and one thing that did not work

- **`/slots` reported busy after the answer was sent** — twice. First a `Session`
  built per request (4+ GiB of KV; `cudaFree` synchronises). Then again, because
  `assert_idle` is the *first* line of the benchmark's next call: the window is
  microseconds. The busy counter now drops *before* the terminal event.
- **The server hard-required an MTP head** once prefill's tail went through the
  fused round. `has_mtp()` selects a plain path; verified on the 0.8B.
- **Keeping the fused graph cache across `Session::reset()` crashes the process**
  on the next speculative request. It looks like the obvious optimisation — the
  shapes recur and the session tensors survive a reset — and it is not. Reverted;
  the cost is a graph rebuild per request. Recorded so the next attempt starts
  from "this was tried".

## A real bug in sampled speculation: drafts conditioned on the wrong token

The gate sweep pointed at it. The fused chain's first link is fed by the
in-graph `argmax -> get_rows`, so every draft is conditioned on the trunk's
ARGMAX at that position. At temperature the committed token is *sampled* and
diverges from the argmax roughly half the time on flat text — and then the
drafts carried into the next round are conditioned on a token that was never
committed. Not improbable: wrong.

Two changes, both measured on the box's benchmark at temperature 1.0:

1. **Drop drafts when the committed token differs from the argmax they assume.**
   Acceptance 0.37 -> 0.49-0.54 immediately.
2. **Cap sampled chains at depth 2** (greedy keeps its configured depth; the
   losslessness gate is unchanged, 8/8). Deep chains are built to be thrown
   away half the time. Depth sweep at 32K: d1 44.0 (acceptance 0.78 — exactly
   production's figure, confirming the conditioning analysis), d2 47.1, d3 44.3.

| decode, temp 1.0 | before | after | prod |
|---|---|---|---|
| depth 0 | 44.3 | **47.7** | 32.4 |
| depth 32K | 43.5 | **46.8** | 52.7 |

The remaining ~11% at depth is structural: llama.cpp drafts *after* sampling
with the committed token (always correctly conditioned, variable length,
p-min gated), where the fused chain drafts before. Closing it means a
post-commit drafting pass for sampled requests — the standalone MTP graph the
spec path already has — at ~6 ms per draft step. Estimated marginal at current
numbers; recorded as the known next lever rather than attempted.

## Session prefix reuse — the 1.3-second revisit, matched

The engine kept one session but reset it on every request, so every turn of a
conversation re-prefilled the whole history: 24 seconds at 32K. llama.cpp's
session cache is why prod revisits a 27K conversation in 1.3 s (ENGINE.md's own
measurement), and for the owner's stated workload — coding chats that extend
turn by turn — this was the largest operational gap in the engine, more than any
decode number.

The worker now keeps `history`: the exact tokens whose state sits in the
session's caches, extended as the state advances (per round, `batch[..n_keep+1]`
— the tokens that survive the rollback). A new prompt that *extends* the history
prefills only its suffix; anything else resets. The recurrent layers make the
rule strict — their state cannot be rewound to an arbitrary point, so a partial
prefix match cannot be salvaged the way a pure-attention engine could truncate
its KV cache.

Correctness gate first, on CPU: a warm continuation is byte-identical to a cold
run of the same full prompt. Then the 27B:

| | prompt tokens | wall |
|---|---|---|
| turn 1 (cold) | 31,851 | 24.4 s |
| turn 2 (warm) | 31,908 | **0.9 s** |
| turn 3 (warm) | 31,950 | 0.1 s |

27x on the second turn, at parity with prod. What this is not, yet: an M6
host-RAM tier. One conversation is cached — the one in the session — so
alternating between two long conversations re-prefills each time. The full M6
(store KV + recurrent states per conversation in host RAM, restore on match) is
the follow-on; this covers the dominant single-user pattern.

## Multi-conversation cache: a session pool, not a host-RAM copy

The plan was M6's host-RAM tier: snapshot the session's caches to host memory on
a conversation switch, restore on return. Built, and correctness-gated on CPU
(A/B/A alternation, warm return byte-identical to cold, 0.4 s vs 6.4 s). Under
tensor parallelism it cannot work: the meta backend's split-tensor get/set
handles axes 0 and 1 in three dimensions, and the GDN state is 4-D and split on
axis 2 — `GGML_ASSERT(tensor->ne[3] == 1)` at ggml-backend-meta.cpp:1441. That
is the fourth meta-backend limit this project has hit; this one was routed
around rather than patched.

The route-around is better than the original plan: a **pool of whole sessions
resident in VRAM**, one conversation each, switched by pointer. No copy at all —
faster than any PCIe transfer could be — and it works identically under TP.
Slot choice is longest-full-prefix match, LRU eviction. Pool size follows VRAM:
two slots fit at 32K context (~2.9 GiB per card each on top of 16.46 GiB of
weights), one above ~70K; `TANDEM_SESSIONS` overrides.

Measured on the 27B at `-c 32768`, tensor parallel (A and B are separate ~31K
conversations):

| | wall |
|---|---|
| A turn 1 (cold) | 24.7 s |
| B turn 1 (switch away) | 23.4 s |
| **A turn 2 (return)** | **0.9 s** |

The host-RAM snapshot tier is kept for single-device deployments, where the
prefix copy works and one card cannot afford a second resident session. The
losslessness gate is unchanged (8/8) and the CPU restore gate is byte-identical.

Context-size trade the owner should know: `-c 32768` buys two switchable
conversations; `-c 65536+` buys one longer one (in-session turn reuse still
applies either way).

## The thinking-mode caveat: investigated, then eliminated

The caveat as recorded — "the template strips `<think>` from prior turns, so
chat-with-thinking cannot prefix-match" — was asserted, not tested. Testing it
found something better.

The template does not strip: it renders prior assistant turns as
`<think>\n{message.reasoning_content|trim}\n</think>\n\n{content|trim}`, with
`preserve_thinking` defaulting on. The reasoning survives — *if the message
carries it*. The server was returning the raw generation (reasoning and answer
fused) in `content`, so the re-render wrapped it in an empty think block and
diverged from the session's state at the first reasoning token.

The fix is what a correct OpenAI-compatible server does anyway: split the
generation at `</think>` and return `reasoning_content` separately (as the Qwen
and DeepSeek APIs do), and accept it back on prior assistant messages. The
trimming in the split mirrors the template's own `|trim`, which is what makes
the round trip token-exact. A unit test asserts byte-exactness:
`render(turn2) == render(turn1) + generated_bytes`.

End to end on the 27B (29K-token conversation, thinking on, client round-trips
the message exactly as returned):

| | wall |
|---|---|
| chat turn 1 (cold) | 27.8 s |
| **chat turn 2** | **1.9 s** |

Caveats that remain, stated precisely: streaming responses do not yet split
reasoning from content (non-streaming does); and a client that discards
`reasoning_content` from history falls back to a cold prefill — correct, just
slow.

## A measurement hazard found by accident

The first run of this test sat on port 8020 and came back COLD, with the trace
showing 120- and 17-token foreign prompts evicting the conversation between my
two turns: **other services on the LAN talk to :8020 continuously**, believing
it is production. Any tandem test bound to 8020 inherits that traffic — worth
assuming earlier 8020-bound benchmark numbers carry some contamination risk,
and future payloads should bind 8031. It also means a prod switch gets real
traffic from the first second.

## Streaming now splits reasoning too

The non-streaming chat response learned to separate `reasoning_content` from
`content`; the stream now does the same, labelling deltas inside the opened
`<think>` block as reasoning and everything after `</think>` as content. The
marker can arrive split across SSE chunks ("...</th" then "ink>..."), so the
splitter holds back up to seven trailing bytes until the next chunk decides
whether they are the marker or ordinary text. Five unit tests cover the
boundary cases — marker split three ways, a false start ("</thing>"), and a
generation cut off mid-think — and a live SSE run confirms deltas carry the
right field. Cut-off semantics were also aligned: under thinking, a generation
that never closes its block is all reasoning, in both response shapes.

## Where "fully operational replacement" honestly stands

Done and gated: OpenAI-compatible serving (chat + completions, streaming with
reasoning split, tokenize/detokenize, slots), sampling with llama.cpp-matched
filter semantics, speculation at any temperature (distribution-preservation
verified on the 27B), warm multi-turn conversations in all three shapes (raw,
chat, chat+thinking: 1.9 s on a 29K revisit), multi-conversation switching via

# 2026-08-20: M5d — batched multi-stream decoding works

The capability that was "the one class where the replacement claim does not
hold" now holds at the compute level, and the route in was the observation that
the batch shape was already latent in the session layout: the recurrent-state
tensors carry a slot dimension for rollback snapshots, and a batch session is a
session whose slot dimension is the *sequence* dimension.

`build_inner` gained a `SeqMode`:

- `Single` — everything before today: one sequence, slot 0 live, K snapshots.
- `Slot(i)` — one sequence prefilled into slot i of a shared session, one
  snapshot (its live state). Used to prefill each batch member.
- `Batched` — t_len tokens, one per sequence: the GDN op runs in its
  `[S, H, 1, n_seqs]` form with `state [S, S, H, n_seqs]` and K = 1, the conv
  window and state write back per-slot in one copy each, and everything else —
  attention, FFN, sampling — was already per-token, since position, mask row and
  KV write row were always per-token inputs. Each sequence owns a region of the
  shared KV cache; the mask keeps it inside its own region.

The `ne[3]` conflict that blocked this on paper resolved cleanly: snapshots and
sequences never coexist, because batch mode does not speculate (K = 1).

**Correctness gate** (`tandem batchtest`): the same prompt decoded greedily
through the single path and as every slot of an N-way batch must produce
identical tokens from every slot. Passes on CPU (0.8B, 3-way) and on the 27B
under tensor parallelism (4-way) — byte-identical everywhere, which rules out
cross-sequence contamination of state, mask or KV.

**Aggregate throughput, 27B, tensor parallel, greedy:**

| batch | seq ctx | ms/round | aggregate |
|---|---|---|---|
| 1 | 2048 | 25.6 | 39.0 tok/s |
| 2 | 2048 | 28.0 | 71.4 |
| 4 | 2048 | 32.4 | 123.3 |
| **8** | **2048** | 46.1 | **173.5** |
| 4 | 8192 | 33.4 | 119.9 |
| **8** | **8192** | 48.5 | **165.0** |
| 4 | 16384 | 34.9 | 114.6 |

The M5 gate asked for >150 tok/s aggregate against llama.cpp's ~101: **165-173
at 8-way**, and the step-cost curve from days ago predicted this almost exactly
(it forecast 198 at 8-way under ideal scaling; the difference is masks over the
whole combined cache).

**What remains for full multi-user serving:** the HTTP scheduler — routing
concurrent requests into batch slots, interleaving chunked prefills with decode
rounds, per-slot samplers. That is engine-loop code on top of a now-proven
compute path, with no remaining graph or backend unknowns. Batch mode does not
speculate; a single active request still takes the speculative single-sequence
path at 64-70 tok/s.

## M5d complete: the scheduler serves concurrent requests through the batch path

The compute path got its scheduler. The engine's dispatcher now watches for
overlap: a request arriving while another is queued sends the whole group
through `run_batch`, which owns a lazily-created batch session (~2.6 GiB of
VRAM, never paid by a box whose requests never overlap). Its loop is the
scheduler: admit arrivals into free slots (zeroing the slot's recurrent state
through a graph — limit #4 means the host cannot write it), feed one 256-token
prefill chunk per pending request, then run one fixed-width decode round for
everyone ready. Fixed width — dead slots carry a dummy token — keeps batch
decoding at exactly one cached graph; chunked prefill bounds how long any
request can stall the others.

Admission needed one more model primitive: `zero_seq_slot`, a per-slot state
reset via `cpy(scale(view, 0), view)` per recurrent layer, because a fresh
sequence must start from zero state and a split 4-D tensor cannot be written
from the host.

Measured end to end over HTTP on the 27B, tensor parallel:

| | aggregate | wall |
|---|---|---|
| 4 concurrent x 96 tok | 111-112 tok/s | 3.5 s (serial would be ~10 s) |
| 8 concurrent x 96 tok | **153.5** / 112.9 tok/s | 5.0 / 6.8 s |

The M5 gate's >150 aggregate (llama.cpp ~101) is met through the real HTTP
path at 8-way, and by the raw compute path at 165-173. Batch mode does not
speculate; single requests keep the speculative fast path, and the
single-request losslessness gate still passes 8/8 after the dispatcher change.

Sampling in batch mode is per-slot host-side (each request has its own seeded
sampler over its logits slice), so mixed greedy/sampled batches work. Requests
larger than a batch slot's region (8K by default, `TANDEM_BATCH` for the slot
count) are the pool path's job, not the batch path's.
